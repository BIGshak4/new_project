# The judge moves from Claude Opus 5 to Claude Opus 5.5 — 1 October 2026

Written for Shaked and Harel. Shaked asked for the grader to move to Opus 5.5. The engine's rule is that the judge
changes only on numbers, so the 13-answer review set (`scripts/p2_review_set.py`, the same set used for the Sonnet
comparison on 26 September) was run on both models back to back, on the same answers, with the same prompts.

## The numbers

| | Opus 5 | Opus 5.5 |
|---|---|---|
| Bands (STRONG / PARTIAL / WEAK) matching the expected band | 13 of 13 | 13 of 13 |
| Bands identical between the two models | | 13 of 13 |
| Misconception keys found | | identical sets on all 13 (order differs) |
| Correctness scores | | within 0.05 on every answer |
| Rubric level estimate | | one level lower on 4 strong answers (2 vs 3, 3 vs 4); the band and the skill evidence come from correctness and the misconceptions, not from this field |
| Behaviour signals on correct answers | "verified_with_example" on most | sparser (empty on three); these feed the tips, not the grade |
| Model time for the 13 | 66 s (5.1 s per answer) | 78 s (6.0 s per answer) |
| Cost for the 13 | $0.19 | $0.20 |
| List price per million tokens (in / out) | $5 / $25 | $4 / $20 |

Reading: the two models grade the same. Opus 5.5 is a little slower per answer from this machine and a little
cheaper per token; on the whole practice loop the grade still arrives in about 8 seconds.

## What changed

- `app/config.py`: the default judge is `claude-opus-5-5`. The prose roles (card, tip, follow-up wording) stay on
  Sonnet 5 as before.
- `app/engine/providers.py`: Opus 5.5's price in the cost table, so usage accounting is right.
- `backend/.env` on the development machine: `ANTHROPIC_MODEL=claude-opus-5-5`.
- The screenshot harness labels its scripted grader as Opus 5.5 so the practice screen reads as it will in
  production.
- Nothing in the evaluator, the prompts, the scoring or the thresholds changed. 794 offline tests pass.

## What only Shaked can do

Render sets the judge through the environment variable `ANTHROPIC_MODEL`, and it is currently set to `claude-opus-5`
there (`/health` reports the evaluator model). In the Render dashboard, Environment, set `ANTHROPIC_MODEL` to
`claude-opus-5-5` (or delete the variable so the code's default applies) and let it redeploy. Then
`https://jobrun-api.onrender.com/health` should show `"evaluator": "claude-opus-5-5"`. Until then production keeps
grading with Opus 5, which is fine.

## If it ever needs to go back

Set `ANTHROPIC_MODEL=claude-opus-5` on Render and in `.env`; nothing else moves. Attempts already graded keep the
model name they were graded with in the submission record, so the two periods stay distinguishable.

## Addendum, 3 October: stricter on incomplete answers

The live trial's interview answers are a stock sentence plus the reference solution cut at 180 characters, so they are
incomplete on purpose. Graded side by side on the same three answers:

| Question | Opus 5 | Opus 5.5 |
|---|---|---|
| Modulo-6 counter | PARTIAL (1.0) | PARTIAL (0.95) |
| Setup, hold, max frequency | STRONG (0.95), "the answer is truncated mid-sentence" | PARTIAL (0.9), "cut off before it explains why slowing the clock does not fix hold" |
| Masked equality | STRONG (0.9), "omits the intermediate vector" | PARTIAL (0.85), same gap |

Both judges see the same gaps; Opus 5 still called two of them STRONG, Opus 5.5 does not. With complete answers the
two agreed on 13 of 13 bands. Consequence: an interview skill backed by a single answer counts as assessed only when
that answer is STRONG, so incomplete single answers now leave the report at "not enough evidence yet" instead of a fit
score. Students will see PARTIAL a little more often for answers that skip a requested part; that matches the rubric.

## Addendum, 3 October (evening): grader instructions v2, worked examples are confirmation

Shaked's decision: "if the answer is good we don't need an example and it can be a strong answer". The grader's
instructions got a new version (`evaluator.v2.md`, v1 kept): the rubric criteria for worked examples (rows, traces,
outputs on listed inputs, an intermediate vector) are satisfied by a correct method that settles them; a missing
example is deducted only when the method is wrong or unclear, or the example would have exposed a mistake; the
explanations a question asks for stay required; depth measures reasoning, not the volume of examples. Same model
(Opus 5.5), same thresholds, same controller. The judge changes only on numbers, graded back to back:

| | v1 | v2 |
|---|---|---|
| Review set, bands matching the expected band | 13 of 13 | 13 of 13 |
| Review set, bands identical between the versions | | 13 of 13 |
| Review set, depth on the correct answers | 0.6 to 0.75 | 0.7 to 0.8 (up by 0.05 to 0.15) |
| Review set, "code only, correct, no explanation" | PARTIAL (0.6 / 0.1) | PARTIAL (0.7 / 0.2): an explanation is substance |
| Pilot text answers (12) | | 11 same band; one array-bound answer WEAK to PARTIAL (the fix was right) |
| Pilot photo answers, correctness | 0.35 to 0.85 | 0.45 to 0.85: interrupt-priority 0.6 to 0.85, enabled-decoder 0.62 to 0.8, sensor-majority 0.35 to 0.45 and 0.45 to 0.75 |
| Pilot photo answers, band | 4 WEAK, 4 PARTIAL | 1 WEAK, 7 PARTIAL |

Reading: a correct design is no longer marked down for the rows and outputs it did not write out, and the sensor
circuits that were WEAK are PARTIAL. None of the photo answers reached STRONG, because STRONG also needs depth of
0.55 and these answers carried no written reasoning: the "why valid is needed" and "why XOR is not enough" the
questions ask for. One sentence of that reasoning would carry the interrupt-priority answer (0.85 / 0.45) over.
Cost of the comparison: about $1.20.
