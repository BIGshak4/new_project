# Guided practice and assistant handoff — 2026-09-19

## Product behavior

The candidate reads a question, starts an attempt, and writes one solution. The screen no longer asks for a practice mode or confidence score and does not show automatic follow-up questions. New attempts use the existing `quick` API mode. The deeper backend modes remain available for a future explicitly designed interview experience.

The answer has two parts: an explanation with automatic text direction, and an optional technical editor with line numbers, syntax highlighting, indentation and undo. Supported choices are C, C++, Python, JavaScript, Verilog, SystemVerilog, VHDL and plain text for formulas, truth tables or pseudocode. The code editor itself does not compile or execute code. A separate circuit drawing/simulation editor and private answer-image attachments have now been added; see [the current handoff, section E](shaked-human-review-handoff.md#e-circuit-drawing-simulation-and-answer-images-new) for the complete visual-answer contract and remaining AI work.

Code stays left-to-right, while Hebrew reasoning can remain right-to-left. The client serializes both parts into the existing answer string using a fenced code block. Existing answers remain readable. The submitted string, including fences, has the existing 20,000-character limit. Draft recovery, idempotency keys and interrupted-submission recovery are retained. No database migration is required.

C and C++ now have local completion sources for keywords, common standard-library names, loop/conditional snippets, and words already present in the current code. Python and JavaScript retain their own language completions. Suggestions open while typing or with Ctrl+Space, and Enter accepts one. This does not require a model API; it is not a language server and does not resolve types, members or external project symbols. Comments and string literals suppress the C/C++ sources. Standard-library suggestions name their required headers rather than inserting includes automatically.

After submission, the heading explicitly confirms that the answer is saved, and demo mode explicitly says it has not been assessed. The submitted answer and the reference are named separately. A prominent comparison button reveals the reference below the saved answer through the existing authenticated endpoint. It remains an explicit action, and revealing it after submission does not change the recorded pre-submission assistance.

## Progressive hints and solution exposure

Hints are authored, question-specific bank content, requested sequentially through the existing hint endpoint. They are not generated by the placeholder assistant. The UI shows which hint comes next, how many have been opened, and whether the reference solution has been revealed.

The backend already records assistance at submission time. `SubmissionView` now exposes the persisted `hints_seen` and `reference_seen` snapshot; the client tolerates older API versions while a deployment rolls out. Showing a solution after submission must not retrospectively change the evidence attached to that answer.

Current `EvidenceParams` assistance multipliers are:

| Hints seen | Assistance multiplier |
| --- | --- |
| 0 | 1.0 |
| 1 | 0.8 |
| 2 | 0.6 |
| 3 | 0.4 |

These are evidence weights, not a displayed percentage grade. The final evidence also depends on mode, familiarity and exposure risk. In particular, `quick` currently has a base weight of 0.3. Revealing the reference before answering makes the answer unsuitable as evidence of independent mastery. It can still be saved as assisted practice. These are existing calibration choices; Shaked can revise them after expert evaluation rather than treating this table as a final scoring policy.

## Demo behavior and language

The previous English paragraphs came from `DemoProvider`, whose responses were fixed demonstration strings. They did not evaluate the candidate's actual understanding. The regular practice UI now hides these demonstration grades, feedback and follow-up questions. The progress screen likewise explains that real skill assessment is pending. Saved solutions and assistance history remain accessible.

The scripted provider now supports Hebrew using the trusted practice-language instruction, so its developer-facing output also follows the selected language. Previously stored English demonstration responses are not rewritten. Old deep attempts retain their backend follow-up data for export and review, but the current UI offers a fresh one-answer practice flow instead.

The backend still runs its existing scripted POC pipeline while `LLM_PROVIDER=scripted`; hiding its output does not turn it into a real evaluator or remove prior demo skill records. Keep demonstration learning data separate from the real pilot, or explicitly reset it with the owners' approval before using profiles for real assessment. The current UI's demo state comes from server health; historical provenance needs to be handled before switching a mixed dataset to a live provider.

## Dedicated assistant area

An area titled “Practice assistant” is part of the question workspace. While the provider is scripted it clearly says the assistant will be connected later. There is no fake conversation or enabled chat box pretending to call a model. Once a real provider is configured, existing submission feedback has a dedicated destination here.

Interactive guidance still needs a real authenticated conversation endpoint and UI. Suggested implementation contract for Shaked (not the only valid design):

1. Authenticate using the existing Supabase bearer token and verify ownership of the attempt on the server.
2. Resolve question, attempt language, submitted answer, and already revealed hints from trusted server state. Do not trust a client-supplied user ID or assistance count.
3. Distinguish unsubmitted drafts from submitted answers. Sending a draft to the assistant must not silently submit or grade it.
4. Make guidance progressively more explicit. Persist any additional assistance the assistant gives before allowing that answer to count as independent evidence. Do not let chat bypass the recorded hint/reference exposure policy.
5. Require an explicit solution reveal before presenting the full reference. Keep hidden rubrics and unrevealed answers on the server.
6. Respond in the attempt language, keeping code and standard technical terms in their appropriate language. A language-switch policy for an already started attempt should be explicit.
7. Store model/prompt version, assistance level and enough provenance to audit feedback. Separate real and scripted assessments, and use bounded conversation summaries rather than unbounded history.
8. Add request limits, model budgets, failure/retry behavior and expert-reviewed evaluations before enabling the assistant for real candidates. Keep provider keys server-side.

No paid API or hosting plan was activated. Visual-answer schema/Storage migrations were subsequently applied; see the current handoff before deployment.
